# Product Requirements Document (PRD)

## MVP «Запись на звонок»

---

## 1. Общее описание

Тестовый MVP-сервис для бронирования временных слотов. Упрощённый аналог Cal.com.

- **Владелец календаря (owner):** имеет настройки доступности и публичную страницу для записи.
- **Публичная страница владельца доступна по `uuid`** — случайному UUID v4, не связанному с PII.
- **Гость (guest):** выбирает слот и оставляет своё имя и email для бронирования.
- **Авторизация и личные кабинеты отсутствуют.** Это учебный demo: не разворачивать его в публичной или общей сети и не использовать реальные персональные данные.
- **Личный кабинет владельца (админка) доступен по URL `/office` без аутентификации и привязан к владельцу, UUID которого указан в `config.yaml` (admin.owner_uuid). В MVP это seed-владелец Bob.** Он показывает email гостей; сетевую изоляцию demo обеспечивает окружение запуска. Приветственная страница проекта доступна по корневому URL `/`.
- **Интеграции с внешними календарями (Google/Apple) отсутствуют.**
- **Тестовые владельцы создаются через миграции при старте приложения.**
- **Гость не становится владельцем автоматически.** Создать собственную страницу владельца можно явно через форму «Создать свой календарь». При создании владельца ему автоматически создаются два события по умолчанию («Короткая встреча» на 15 минут и «Стандартная встреча» на 30 минут) — как у seed-владельца Bob.
- **Время отображается в часовом поясе владельца**, заданном в настройках. В базе все времена хранятся в UTC.

## 3. Технологический стек

- **Backend:** Go 1.26 (стандартная библиотека `net/http` + `gorilla/mux` или аналог по согласованию).
- **Архитектура:** Clean Architecture (Domain → Usecase → Interfaces → Infrastructure).
- **Database:** SQLite (файл `data/data.db` в рабочей директории).
- **Frontend:** Single Page Application на чистом HTML/JS/CSS (vanilla JS).
- **API-контракт:** TypeSpec (`api/`) с генерацией OpenAPI 3.0 (`api/generated/openapi.yaml`).
- **Конфигурация:** YAML-файл `config.yaml`.
- **Инфраструктура:** Docker, multi-stage Dockerfile.
- **Rate limiting:** in-memory rate limiter на базе `golang.org/x/time/rate`.
- **Deployment:** один экземпляр приложения с одним локальным SQLite volume; горизонтальное масштабирование не поддерживается.

```

Все маршруты, кроме `/api/*`, `/healthz` и `/static/*`, отдают `index.html`. Фронтенд (vanilla JS) самостоятельно разбирает URL и отображает нужную страницу:
- `/` — приветственная страница проекта: описание MVP, ссылка на список доступных календарей и на личный кабинет владельца.
- `/office` — личный кабинет владельца, указанного в `config.yaml` (admin.owner_uuid).
- `/owners` — публичный список активных владельцев.
- `/owners/new` — форма создания нового владельца.
- `/owners/{uuid}` — публичная страница записи к владельцу.

**Алгоритм создания владельца (Use Case Layer)**

1. **Валидировать входные данные:** `name` непустой, `email` соответствует формату email.
2. **Проверить уникальность email:** `OwnerRepository.GetByEmail` — при занятом email вернуть `409 Conflict`.
3. **Создать владельца:** `OwnerRepository.Create` с новым UUID v4 и дефолтными настройками календаря из `config.yaml` (`default`).
4. **Создать события по умолчанию:** для каждого события из `config.yaml` (`default.events`) создать событие с UUID v4 и привязкой к `owner_id` нового владельца. В MVP это «Короткая встреча» (15 минут) и «Стандартная встреча» (30 минут).
5. **Зафиксировать транзакцию:** создание владельца и всех default events выполняется в одной транзакции. При ошибке ни владелец, ни часть набора событий не сохраняются.
6. **Вернуть созданного владельца** (`uuid`, `name`, `settings`) без email — HTTP `201 Created`.

## 5. HTTP-статусы и ошибки

| Код | Когда |
|-----|-------|
| 200 OK | Успешный GET/PUT |
| 201 Created | Успешное создание ресурса |
| 400 Bad Request | Невалидные входные данные: email, UUID, дата, время, длительность, название события |
| 404 Not Found | Owner, guest, event, booking или страница не найдены |
| 409 Conflict | Email/название события заняты, слот занят, день выходной, слот не входит в рабочие часы |
| 429 Too Many Requests | Rate limit exceeded |
| 500 Internal Server Error | Внутренние ошибки сервера |

Детальная схема тела ошибки (`ErrorResponse`) и сопоставление ошибок с HTTP-статусами описаны в TypeSpec (`api/errors.tsp`).

## 6. Rate Limiting

- Применяется к `POST /api/bookings`, `POST /api/owners`, `POST /api/owners/{uuid}/events` и `POST /api/admin/events`.
- Лимит: 30 запросов в минуту с одного IP, burst = 10.
- При превышении возвращается `429 Too Many Requests`.
- Реализуется middleware на базе `golang.org/x/time/rate`.

## 7. Алгоритм генерации слотов (Use Case Layer)

1. **Получить владельца** по `uuid`.
2. **Получить событие** по `event_uuid` и проверить, что оно активно и принадлежит владельцу.
3. **Загрузить настройки** владельца (`work_start`, `work_end`, `timezone`, `working_days`) и длительность `event.duration_minutes`.
4. **Определить диапазон дат** — 14 дней начиная с текущей даты (включительно) в часовом поясе `timezone`.
5. **Получить существующие бронирования** владельца за весь диапазон дат (UTC).
6. **Для каждой даты в диапазоне:**
   1. Определить день недели в часовом поясе `timezone`.
   2. **Проверить рабочий ли день** по `working_days`. Если нет — вернуть пустой массив для этой даты.
   3. **Преобразовать `work_start`/`work_end`** в UTC для данной даты и часового пояса.
   4. **Разбить рабочий интервал** `[work_start, work_end)` на слоты длины `event.duration_minutes`.
   5. Для текущего дня пометить слоты, которые уже начались или полностью прошли, как `unavailable` с `reason: "past"` (граница: текущее время в часовом поясе owner).
   6. **Пометить занятые слоты.** Слот `[slot_start, slot_end)` пересекается с бронированием `[booking_start, booking_end)`, если:
      ```
      slot_start < booking_end AND slot_end > booking_start
      ```
      Пересекающиеся слоты помечаются как `unavailable` с `reason: "booked"`.
   7. **Сохранить все слоты** для этой даты в виде массива объектов `{time, status, reason}` в часовом поясе владельца. Слоты со статусом `available` не содержат `reason`.
7. **Вернуть результат** — объект со слотами, сгруппированными по датам.

## 8. Алгоритм создания бронирования (Use Case Layer)

1. **Получить владельца** по `owner_uuid`.
2. **Получить событие** по `event_uuid` и проверить, что оно активно и принадлежит владельцу.
3. **Валидировать входные данные:**
   - `guest_email` соответствует формату email.
   - `date` и `start_time` валидны.
   - `date` находится в пределах следующих 14 дней от текущей даты (включительно).
4. **Проверить IANA time zone:** `owner.timezone` должна быть валидной. Если локальное `date` + `start_time` попадает в DST-gap или неоднозначный час при переходе на зимнее время, вернуть `400 Bad Request`.
5. **Преобразовать `date` + `start_time`** в UTC с учётом `owner.timezone`.
6. **Вычислить `end_time`** = `start_time + event.duration_minutes`.
7. **Проверить, что день рабочий** в `owner.timezone`.
8. **Проверить, что слот внутри рабочих часов:**
   - `start_time >= work_start` и `end_time <= work_end` для данной даты.
   - `start_time` кратен `event.duration_minutes` (граница слота).
   - `start_time` не в прошлом (если `date` — текущий день).
9. **Создать или найти guest** по `guest_email`.
10. **Вызвать `BookingRepository.CreateBooking`** — транзакция с проверкой пересечений и `UNIQUE` constraint.
11. **Вернуть созданное бронирование** в UTC.
12. **Вывести mock email** в логи.

### 9.0. Приветственная страница (`/`)

Открывается по корневому URL. Светлая тема. Содержит:

- Блок «О проекте» — описание MVP (аналог Cal.com, бронирование слотов без регистрации).

### 9.1. Личный кабинет владельца (`/office`)

Открывается по URL `/office` и привязан к владельцу, UUID которого указан в `config.yaml` (admin.owner_uuid). В MVP это seed-владелец Bob. Интерфейс состоит из двух вкладок/секций.

#### Wireframe / Layout

```
+-------------------------------------------------------------+
|  Calendar MVP Admin  |  [Бронирования]  [Типы встреч]       |
+-------------------------------------------------------------+
|  Владелец: Bob Jones (Europe/Moscow, 09:00–18:00)           |

|  +-----------------------------------------------------+    |
|  (пустое состояние: «Нет предстоящих бронирований»)         |
+-------------------------------------------------------------+

+-------------------------------------------------------------+
|  Вкладка «Типы встреч»                                      |
|  +-----------------------------------------------------+    |

**Вкладка «Бронирования»**

- Список отсортирован по времени начала (ближайшие сверху).

**Вкладка «Типы встреч»**

  - `Название` (обязательное).
  - `Описание` (опциональное).
  - `Длительность (мин)` (обязательное, целое > 0, например 15, 30, 45).
  - Кнопка «Добавить».
- После создания система генерирует UUID и показывает его в списке как `id`.
- При ошибке 409 под формой отображается сообщение «Событие с таким названием уже существует».

## 10. Нефункциональные требования

- Приложение запускается одной командой `task docker:run` (после сборки образа `task docker:build`); локально для разработки — `task run`.
- SQLite-база инициализируется автоматически при старте.
- Миграции и тестовые данные выполняются при первом запуске.
- Публичные списки бронирований доступны без авторизации.
- Все времена хранятся в UTC в базе данных.
- Время на фронтенде отображается в часовом поясе владельца.
- **Бизнес-логика (use cases) покрывается юнит-тестами.** Для тестов репозиториев используются in-memory stub-реализации (mock/fake), чтобы не зависеть от SQLite.
- Поведенческий набор тест-кейсов описан в `docs/TESTING.md`; приложение должно проходить его (API, конкурентный доступ, UI-визард).
- Приложение поддерживает graceful shutdown.
- Есть endpoint `/healthz`.
- Rate limiting защищает публичные мутации.
- Образы в Dockerfile пинятся конкретными версиями.
- SQLite-файл сохраняется через Docker volume.
